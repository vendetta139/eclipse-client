# Правила разработки и публикации релизов

Этот файл обязателен к соблюдению во всех следующих сессиях.

## Жёсткий запрет на автопубликацию

**ЗАПРЕЩЕНО** без прямого подтверждения пользователя:
- выполнять `git push` в любой удалённый репозиторий;
- изменять `version.json`;
- мерджить ветку `beta` в `main`;
- создавать, изменять или публиковать релизы на GitHub (`gh release ...`).

## Рабочий цикл (ветка `beta`)

1. Вся разработка, правки, рефакторинг и эксперименты ведутся **только в ветке `beta`**. Ветка `main` хранит только стабильный релиз.
2. Для тестовых сборок в `gradle.properties` используется бета-суффикс (например, `mod_version=2.0.1-beta.1`, следующая тестовая сборка — `2.0.1-beta.2` и т.д.).
3. После внесения правок:
   - собрать проект командой `./gradlew build` (на Windows `.\gradlew.bat build`);
   - задача `copyToGameMods` автоматически удалит старый `eclipse-client-*.jar` из `mods/` и скопирует актуальный бета-`.jar` без дублей;
   - **не трогать** `version.json` и **не пушить** изменения на GitHub;
   - кратко сообщить пользователю путь к собранному `.jar` и что именно нужно проверить в игре, после чего ждать подтверждения.

## Процедура релиза (только по команде пользователя)

Выполняется **только** после явного подтверждения пользователя (например: «работает, релизим» или «работает, релизим 2.0.1»):

1. В `gradle.properties` убрать суффикс `-beta.*` (установить релизную версию, например `mod_version=2.0.1`).
2. Закоммитить изменения в `beta`.
3. Выполнить `./gradlew clean build` и убедиться, что в `build/libs/` собрался финальный `.jar` без `-beta`.
4. Обновить `version.json` в корне проекта (поставить релизную версию и короткий живой changelog без воды и эмодзи).
5. Переключиться на `main`, смерджить `beta` в `main` (обновить `version.json` на `main`), запушить `main` (и при необходимости `beta`) на GitHub.
6. Создать GitHub Release (например, `v2.0.1`) с финальным `eclipse-client-<version>.jar`, оформив описание строго по правилам раздела «Правила написания Changelog для релизов на GitHub».
7. При переходе к следующим правкам снова вернуться в ветку `beta` и выставить следующую бета-версию (например, `2.0.2-beta.1`).

## Правила написания Changelog для релизов на GitHub

Эти правила обязательны для каждого релиза на GitHub (и для `CHANGELOG.md`, если он ведётся).

### 1. Стиль, тон и анти-ИИ правила
- **Пиши от первого лица и живым языком.** Используй простые глаголы действия: «сделал», «убрал», «починил», «перекрасил», «добавил», «теперь работает так». Стиль — как пост живого разработчика в Discord или Telegram, без сухого официоза.
- **Полный запрет на канцелярит и пассивный залог.** Запрещены рекламные вступления («Мы рады представить…», «В этом масштабном обновлении…», «Новый уровень опыта»), пафосные прилагательные («флагманский», «бесшовный», «элегантный», «передовой», «инновационный», «революционный») и казённые обороты («реализовано», «выполнена оптимизация», «переведён на», «а также дорабатывает», «без необходимости», «с ограничением не чаще», «возможной нестабильности»).
- **Никаких эмодзи** в заголовках и пунктах списка.
- **Никаких названий внутренних классов и миксинов.** Не пиши в тексте имена вроде `EclipseClickGui`, `TitleScreenMixin`, `PressableWidgetMixin`, `EclipseColors`, `UpdateChecker`, `RenderUtils` и т.п. Пиши словами, понятными игроку («главное меню», «кнопки и слайдеры», «редактор HUD», «меню префиксов»). Упоминать можно только те файлы и папки, с которыми игрок реально сталкивается сам (`eclipse-client.json`, `mods/`, `.jar`).
- **Короткий ритм без длинных тире-конструкций.** Если предложение получается громоздким или с длинными тире, разбей его на два коротких. Объясняй, что изменилось для игрока на практике, а не пересказывай код.

### 2. Детализация и достоверность
- **Подробно и по делу (без отписок по 3 слова).** Запрещены ленивые односложные пункты вроде «Улучшена оптимизация», «Исправлены баги» или «Обновлён интерфейс».
- Каждый пункт должен раскрывать суть: что именно поменялось, как это работает теперь и какую проблему решает (1–2 полных, понятных предложения на пункт).
- Составлять список **строго на основе реального `git diff main..beta` и коммитов** в ветке — ничего не додумывать и не приписывать лишнего.

### 3. Структура описания релиза на GitHub
1. **Короткий вводный абзац (1–2 простых разговорных предложения):** чему посвящён билд и под какой Minecraft он собран (например, Fabric 1.21.11). Никакого перечисления всех разделов по схеме «Обновление X делает А, убирает Б, а также В».
2. **Группировка по категориям** (добавлять только те разделы, где реально были изменения):
   - `### Добавлено`
   - `### Изменения и интерфейс`
   - `### Оптимизация`
   - `### Исправления`
   - `### Удалено`
3. **В конце короткий блок `### Установка`:** какая версия Fabric Loader и Fabric API нужна и куда положить `.jar`.

### 4. Ориентир по подаче
- **Плохо (ИИ-стиль и пафос):** «✨ Революционный монохромный дизайн подарит вам незабываемый и чистый игровой опыт!»
- **Плохо (сухо и с именами классов):** «Реализован перевод `EclipseClickGui` и `TitleScreenMixin` на палитру `EclipseColors`, а также выполнена оптимизация `HudElement`.»
- **Плохо (слишком кратко):** «Сделал ч/б тему и оптимизировал HUD.»
- **Хорошо:** «Перекрасил весь интерфейс мода в строгую чёрно-белую палитру: меню модулей, редактор HUD, главное меню, кнопки и слайдеры. Активные переключатели и нажатые клавиши в Keystrokes теперь подсвечиваются белой инверсией с чёрным текстом. Превью донат-префиксов с `&`-кодами и `&#HEX` при этом осталось цветным.»
- **Хорошо:** «Убрал лишнюю сборку текста на каждом кадре в виджетах FPS, CPS и префиксов. Теперь строки кэшируются и пересчитываются только тогда, когда реально поменялось число. Файл `eclipse-client.json` больше не перезаписывается на каждый сдвиг ползунка. Настройки сохраняются на диск один раз, когда отпускаешь мышку или закрываешь меню.»

### 5. Разделение для `version.json`
- Полный подробный Changelog пишется для описания релиза на GitHub (и при необходимости в `CHANGELOG.md`).
- В `version.json` (поле `changelog`, которое выводится в игровой чат) добавляются **только 3–4 самых главных пункта в сжатом виде**, чтобы уведомление об обновлении не спамило на пол-экрана в чате.
